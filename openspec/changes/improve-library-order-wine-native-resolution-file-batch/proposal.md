# 统一卡片创建时间排序、Wine 原生分辨率与文件批量操作

## 问题与依据

用户要求 Wine／Desktop 卡片按创建时间从新到旧排列，Wine 提供与 Desktop 一致的 Native 分辨率，文件浏览支持批量操作。

当前 `FileGameRepository.list()` 按游戏名称排序，`FileDesktopDistroRepository.list()` 按属性文件名排序；`Game` 和 `DesktopDistro` 都没有创建时间字段。`GameRuntimeOptionsView.renderBase()` 只列固定尺寸，启动服务先冻结 `LaunchSpec`，随后才打开 `GameSessionActivity`，不能直接把 `native` 交给现有数值尺寸解析器。`GameFileManagerActivity` 的剪贴板仅持有一个 `File`，底层 `BrowserFileOperations` 已有串行操作、根目录保护、同名冲突拒绝和不跟随链接递归等能力。

## 用户可见行为

1. Wine／Desktop 的实际内容卡片在 Native、PRoot、网格和列表中统一按创建时间降序，同一时间以稳定标识排序；改名称、改运行设置、启动、重新安装、刷新和旋转不会使原卡片变成新卡片。新导入／新创建记录进入所属后端列表前方，现有新增／导入操作卡及 Native 固定入口能力保留。
2. Wine 的通用分辨率增加“Native（窗口原生尺寸）”，适用于 Native／PRoot 后端及游戏／Wine 桌面启动。保存的是 `native`，每个新任务按启动窗口的有效像素尺寸生成数值参数；重入既有任务使用原有尺寸。固定尺寸及原默认值保留。
3. App 内文件浏览器增加多选模式、全选／取消全选、退出选择、批量复制／剪切／删除；网格与列表体验一致。复制／剪切后可跨目录粘贴，删除前确认数量及名称。发生冲突不覆盖、合并或自动改名；失败明确报告已完成、失败和未执行项目。

## 范围与非目标

范围为本地 Java 模型、仓库、启动编排、显示配置、文件浏览交互、中英文资源和针对性回归。复用现有文件操作实现，不添加外部文件管理器依赖。文件批量操作不包含批量导入为程序、批量打开、分享、压缩或批量重命名；普通点击／原有长按菜单继续可用。运行中动态改变 Wine 桌面尺寸、桌面运行时／根文件系统更换、组件下载和手柄能力不在范围内。

## 数据与兼容性

新记录持久化毫秒创建时间，更新保留原值。旧记录没有真实创建时间，无法精确还原历史：首次升级读取时使用原记录文件时间一次性补齐，之后固定，禁止每次按修改时间重新排序。批量恢复／导入以本次建立记录的时间为创建时间。Native 固定入口仅在首次建立时获得时间，重复补全不刷新已有时间。

现有存量记录继续可读；创建时间字段增加需要同步严格字段白名单及所有模型复制路径。回退旧版 APK 前需备份记录并移除旧版不认识的新增字段；已选择 `native` 的 Wine 配置需先改回固定尺寸。批量操作不会承诺跨文件系统的整批事务回滚。

## 文档、风险与回滚

无 HTTP 契约变更，`api_docs=N/A`。三项均改变可见行为，`product_docs=Required`，拟在用户最终验收后维护 `docs/product/local-games.md`、`docs/product/desktop.md`、`docs/product/file-manager.md`，当前一致性为 Pending。这些产品文档及产品索引当前缺失，不将计划写成已交付事实。

主要风险是编辑重排、活动会话尺寸错配、批量操作部分完成。通过不可变时间、任务内持久化数值尺寸、整批预检及逐项结果报告约束。代码可按三个能力分别撤回；文件操作已经完成的用户数据变更不能用撤回 APK 回滚，因此保留明确删除确认与失败状态。
