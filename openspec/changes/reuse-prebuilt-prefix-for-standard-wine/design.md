# 设计

## 当前实现

ProotDependencyResolver 已按需获取基础镜像、所选普通 Wine、独立 Box64 和图形包装组件；ProotBindingResolver 将组件挂载到 /opt。rootfs_prefix_warmup.sh 只有 rootfs_hangover_11.16 + hangover 进入预生成模板路径，其他组合在 prepare_external_prefix_template 现场运行 wineboot。restore_wine_prefix.py 的包身份和公共文件来源固定在 Hangover 与 RootFS /usr。

## 实现方案

1. 保持 PRoot 运行链路与组件下载方式。模板选择从单个包名扩展为显式兼容描述：后端、宿主 ABI、Windows prefix 架构、模板修订和所选 Wine 组件身份。
2. 按用户已验证的同架构兼容结论复用初始化骨架。审计现有注册表、system32/syswow64、PE machine 和 DLL 来源；复用兼容骨架，所选 Wine 的系统 DLL 从受校验组件映射补齐。需要不同骨架时离线制备一次，不在用户设备首次准备生成。
3. 扩展打包/恢复元数据，使源文件有明确受信任根（共享镜像或当前固定组件），限制到许可目录，核对每文件 SHA256、大小、类型和路径；禁止任意外部路径输入。新架构不通过删除校验冒充兼容。
4. 已支持普通 Wine/Proton 的准备分支仅执行恢复。没有兼容模板、组件损坏或架构不匹配时明确报错，不回退完整初始化。未纳入适配的自定义 Wine 保持现有行为，并明确覆盖边界。
5. 恢复后生成所选 Wine/翻译器的运行标记；不再进入全量 wineboot 更新分支。正常 Wine 服务启动与首次前缀安装分别观察，不能仅凭准备脚本没调用 wineboot 就判定成功。
6. 模板资产参与配方身份，所选组件摘要参与就绪身份；每游戏独立复制、原子发布，取消失败不污染成功缓存，不覆盖非空 C 盘。

## 编译目标约束（2026-11-08 用户再次明确）

Native glibc_termux_box 与 rootfs_proot 使用各自加载链，禁止交叉消费产物。前者由 Termux glibc 的 ARM64 加载器配合 --library-path 启动 Box64；后者在 RootFS 客体中由客体 libc 和所选 Box64 加载 Wine。ELF解释器相同不能证明可复用，还须核对 RPATH/RUNPATH、编译 prefix、运行时代码中的固定路径、DT_NEEDED、Box64库目录及 Unix/WoW64 架构布局。本轮 syscall 修复面向 rootfs_proot，候选必须按该目标独立构建；给 Termux glibc 构建的现有 Wine 11.19 包不得作为 PRoot 候选或有效 SUD 对照。已有错误目标的主机启动只作为拒绝证据：未进入探针，不能据此认定 SUD 失败。禁止创建加载器软链接、借用另一后端库路径、修改注册表或删库拼装掩盖目标不匹配。
