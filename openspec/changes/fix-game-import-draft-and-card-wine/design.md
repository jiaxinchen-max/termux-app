# 设计（待确认）

## 草稿和正式记录分离
增加独立导入草稿存储，以游戏标识关联游戏及运行配置；正式库枚举不读取草稿。编辑加载可识别本次导入草稿，现有游戏保持从正式库读取。导入阶段不创建正式容器配置，不排队准备任务。草稿允许组件选择及屏幕重建往返，不以 Activity.onDestroy 作为放弃信号。

## 提交与退出
文件导入、嵌入编辑和独立运行配置编辑共享同一保存/放弃边界。显式首次 Save 校验当前游戏和运行配置，先写依赖的配置及 PRoot 容器，再原子发布游戏库记录；发布失败不可留下可见卡片，错误对用户可见。发布成功后清理草稿并启动原有准备流程。已发布后若异步环境准备失败，保留游戏并禁用启动，显示原有失败状态，不能把失败当成功或回退重建。
Discard 明确丢弃新导入草稿；未改动的新导入直接返回同样不发布。保存过的游戏放弃编辑只丢弃当前修改。清理只涉及草稿所有的元数据/封面等私有资料，不能通过通用卸载误删共享 Native 环境或游戏源文件。进程终止遗留的未提交草稿始终不出现在库中；不增加旧数据迁移。

## 卡片信息
后台加载正式 RuntimeProfile 时一并收集 Wine 标识；复用运行组件展示名解析规则，从目录或本地自定义组件获得名称与版本。缺少展示名时显示已保存标识，不猜成默认 Wine。卡片及列表各布局均显示独立 Wine 信息行，例如 Wine 9.3、Proton 11，并保留当前 Native/PRoot 后端信息。未保存选择不影响卡片，保存后的页面恢复和刷新读取正式配置。

## 风险及验证
重点检查运行配置页 Discard 回到父编辑页时草稿已被正确撤销；首次保存必须写入游戏，即使表单字段没有变化。测试保存失败、重复点击、横竖屏及组件选择往返、同一 EXE 重复导入、两种后端、已保存游戏 Discard。覆盖卡片/列表及自定义 Wine 名称解析。验证保留现有强杀编辑/删除行为和未准备禁止启动规则。
当前缺少仓库 Harness 入口、严格验证脚本、OpenSpec CLI 和产品基线，不能宣称严格门禁、独立评审或产品一致性通过；实施后记录可执行的本地测试及 APK 验证。未授权 Git 操作、发布或设备操作。

## 实施及验证补充
用户已批准本方案。实现使用 import-drafts/games、profiles、containers 作为独立草稿存储，编辑和组件选择按草稿身份读取配置；RuntimeEditingStop 也使用相同读取边界，保持编辑即强杀规则。正式记录发布在 GameAssetMutationLock 中进行，与已有孤儿清理串行。
65 项测试通过，含写入故障重试、两种后端、重复导入、已有游戏Discard、横竖屏与组件往返、首次Save、加载前返回、卡片与列表以及Wine切换刷新。APK已本地构建验证，用户手动验收待完成，未上传Release或执行Git写操作。
