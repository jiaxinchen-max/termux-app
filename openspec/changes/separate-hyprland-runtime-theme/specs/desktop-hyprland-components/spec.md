# Hyprland 组件管理规格（用户已批准实施）

## Purpose

为 Android Hyprland 桌面分别提供可信的合成器与主题包身份、兼容约束和更新路径，使用户能够在 App 中明确选择外观、检查安装状态和安全切换，并准确区分 App 发布修订与原生合成器版本。

## ADDED Requirements

### Requirement: 独立组件身份
系统 MUST 分别记录和展示合成器版本、主题包版本及 App 修订；不得以主题或 App 的修订号推导一个不存在的合成器版本。

#### Scenario: 查看 r8 交付身份
- **WHEN** 用户查看使用 r8 m3ww 交付材料的桌面
- **THEN** 显示其实际合成器为 0.57.0-r7，主题为 m3ww-v1，r8 仅作为交付修订，不出现可下载的虚构 r8 合成器。

### Requirement: 独立选择与兼容检查
系统 MUST 在 Hyprland 创建及设置界面分别提供合成器与主题选择，保存每个桌面的组合并拒绝未知或未经登记的组合。

#### Scenario: 选择兼容主题
- **WHEN** 用户为 r7 合成器选择已登记的经典或 m3ww 主题并保存
- **THEN** 重启 App、重命名、复制及修改分辨率后仍保留该组合，后续安装与启动使用相同身份。

#### Scenario: 选择未知组合
- **WHEN** 配置包含未知组件或不兼容组合
- **THEN** 明确报告原因并阻止启动，不静默改用其他版本或主题。

### Requirement: 独立校验和安装
系统 MUST 对合成器和主题分别校验固定资产身份、架构或兼容信息及 SHA-256；主题更新不得重装未变化的合成器，缺失主题资源或依赖不得报告完整安装成功。

#### Scenario: 仅更新主题
- **WHEN** 合成器已通过验证且用户安装另一个兼容主题
- **THEN** 只获取并安装该主题及缺失依赖，合成器文件哈希保持不变。

#### Scenario: 下载或解包失败
- **WHEN** 任一包下载失败、校验失败或包含越界路径、链接或超限内容
- **THEN** 不激活候选或写成功标记，保留原可用组件与选择，并提供失败日志及重试入口。

### Requirement: 可控切换与用户配置保留
系统 MUST 在停止桌面后切换主题，并保留用户修改过的配置；旧桌面首次接入时根据现有主题标记及原有默认识别规则保留有效外观，不可因新增选择字段而自动覆盖。

#### Scenario: 运行中请求切换
- **WHEN** 用户在桌面运行时选择新主题
- **THEN** 提示先停止桌面，不修改当前会话与已激活主题。

#### Scenario: 接入旧桌面
- **WHEN** 原桌面已有 r7 或 m3ww-v1 标记，或存在自定义配置
- **THEN** 识别并保留原外观，将 r7 主题标记解释为经典主题，不修改原 hyprland.lua；未知标记报告错误。

#### Scenario: 回滚主题
- **WHEN** 用户停止桌面并恢复先前可用主题
- **THEN** 使用原合成器与保留的主题配置启动，不要求清除 App 数据或重建容器。

### Requirement: 会话与其他桌面隔离
系统 MUST 将所选身份用于启动和诊断，并保持原生与 PRoot 路由、当前会话就绪和进程清理隔离；本变更不得扩大现有渲染器、USB 或归档支持范围。

#### Scenario: 必要主题服务失败
- **WHEN** 当前主题必需的面板、通知或背景服务退出
- **THEN** 清除就绪状态并记录所选合成器与主题身份，仅清理当前桌面所属服务，其他桌面不受影响。

### Requirement: 公开组件目录与 App 同步
系统 MUST 在独立组件仓库记录当前合成器与主题的真实发布身份、URL、大小和 SHA，并与 App 目录一致；历史实机证据与新版本的验证状态 MUST 分开记录。

#### Scenario: 独立主题公开发布
- **WHEN** 用户授权组件资料与独立主题发布
- **THEN** 发布两个可校验主题归档及源材料，匿名获取的字节与 App 内置包一致，r7/r8 历史资产保留，APK 文件名保持 termux-app_apt-android-7-debug_arm64-v8a.apk。

## 已确认的交付方式修订（download-runtime-assets-on-demand）

用户已确认主题与 API 配套资源改为资产库按需下载，取代本文件此前内嵌主题/CLI/deb 的交付要求。Android API 宿主保留 APK；Linux 下随 App 构建配套包与是否打入 APK 分开处理。最终要求及验收场景以 download-runtime-assets-on-demand 的四项规划为准，历史发布与验证记录保留原意，不声称旧 APK 已外置。
