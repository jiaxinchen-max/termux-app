# 恢复终端模式 X11 启动脚本入口

## 问题与证据

用户报告终端模式的 X11 待机页启动按钮点击无效果，记得原先长按可以选择启动脚本。历史提交 e32a7039 删除了 StartEntryClient 和启动项布局；后续重新加入的按钮在 TermuxActivity.startX11Display 中固定后台执行 termux-x11 :1，TermuxScreenView.setTerminalIdleActions 没有绑定长按。StartEntry、StartEntryArrayAdapter 和文件选择器仍在，但没有启动入口使用它们。

设备只读检查确认：startxserver 脚本仍存在，它运行 termux-x11 :1 后启动 xfce4-session；设备缺少 xfce4-session，且没有启动项配置文件。检查时另有程序会话正在使用 :0，现有 termux-x11 包装脚本发现任意同名服务便退出；这也是固定命令不能可靠表达用户希望启动的会话的原因。没有点击待机按钮复现，没有停止现有会话，不能把观察到的 :0 进程认定为用户此前点击失败的唯一原因。

## 目标与用户可见行为

- 单击启动按钮，运行用户当前选择的本地可执行启动脚本；按钮显示所选脚本名称，未选择脚本时显示中文“启动”、英文 `start`。
- 长按启动按钮，打开脚本选择与管理入口，支持添加、选择、移除启动项并保存选择。
- 没有选择脚本时打开选择入口；脚本已不存在或不可执行时说明原因，不执行其他命令替代。
- 在 TermuxService 持有的独立终端 session 执行脚本；退出桌面时终止并回收该 session，其他终端不受影响。
- 不分析脚本依赖或执行失败原因，不新增失败判定、保留失败控制台或自动修复流程，沿用既有终端行为。

## 范围与非目标

范围限于终端模式 X11 待机页、启动项存储与本地脚本执行接线。UI 模式的待机页、Wine/PRoot 启动、prefix 资产、图形后端、组件仓库不变。不自动安装 XFCE，不修补用户脚本，不增加固定的备用命令，不迁移旧目录，不引入新 HTTP 契约。

## 风险、兼容性与回滚

继续使用现有启动项配置路径 home/.termux/config/.startItemEntries，不增加兼容或自动升级流程。移除启动项只修改配置，不删除脚本。主要风险是选择索引、重建页面后丢失选择、带空格路径被 shell 拆分、脚本 session 未被正确回收，以及误将长按也识别为启动；均纳入验证。

回滚只还原本变更的 Java、布局、文案及测试，不重置用户脚本、配置、RootFS 或 prefix。仓库没有可用的 protected-path 策略，记录实际修改范围并在实施前取得本规划确认；不推断额外路径批准。

## 文档与状态

HTTP 文档 api_docs 为 N/A：本地界面和进程执行，不改变 HTTP 契约。产品文档 product_docs 为 Required，目标为 docs/product/terminal-x11.md；用户验收前保持 Pending。用户随后明确指示只恢复脚本执行和选择，并要求脚本由 session service 持有、退出桌面时回收，作为本规划的范围确认。实施严格按此收窄范围执行。仓库缺少 Harness 引导、严格验证脚本、OpenSpec CLI 和产品基线，不能声称这些门禁通过。
